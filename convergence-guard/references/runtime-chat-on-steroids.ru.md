# Профиль среды выполнения Chat On Steroids

Этот файл описывает локальную интеграцию Chat On Steroids, использовавшуюся в исходной среде разработки Convergence Guard. Она **не** является частью универсального метода.

Читайте этот файл только при запуске Convergence Guard внутри Chat On Steroids.

## Штатный путь выполнения

Используйте Chat On Steroids Core для получения фактов проекта: файлов, кода, журналов, состояния Git, команд и локального состояния.

Для операций Full Mode, которым требуется настоящая изоляция или слепота, используйте штатный механизм `agents`.

## Топология workers в v0.2.1

Обычный проход Full Mode с тремя финалистами использует примерно девять worker-контекстов:

```text
Phase B
3 изолированных worker-контекста причинного поиска
(+1 или +2 только если не пройден шлюз покрытия)

Phase C
1 свежий screener по контракту
1 свежий слепой mapper причинных моделей
(+1 boundary critic только если неоднозначность карты влияет на решение)

Phase D
1 свежий dossier worker на каждого финалиста (2–3)
1 свежий adjudicator по всему slate
(+1 независимое second opinion только при срабатывании условия)

Опционально до поиска
+1 независимый reframe reviewer, если риск ошибочной постановки существенен
```

После нейтрализации кандидатов screener и blind mapper следует запускать одновременно, поскольку каждый из них должен оставаться слепым к результату другого.

Начальная поисковая когорта по умолчанию состоит из трёх **свежих worker-контекстов**, а не пяти. Это требование к числу независимых поисковых контекстов, а не к числу workers, выполняющихся одновременно.

Ёмкость workers в Chat On Steroids является настройкой среды выполнения и может меняться. Если настроенное число одновременных worker-слотов меньше числа свежих контекстов, требуемых стадией, выполняйте эту стадию пакетами в пределах доступной ёмкости, сохраняя те же правила слепоты и границ контекста. Например, при двух слотах начальная поисковая когорта из трёх workers выполняется как `2 + 1`; при трёх и более слотах все трое могут запускаться вместе.

Текущий настроенный предел — **три одновременных worker-слота**, поэтому обычную начальную когорту Phase B из трёх свежих поисковых workers можно запустить одновременно.

Любой более поздний worker в пакетно выполняемой стадии всё равно должен быть свежим и получать только разрешённые для этой стадии входные данные. Он не должен получать результаты или выводы workers, завершившихся раньше, лишь потому, что теперь эти результаты существуют в родительском проходе.

Аналогично, примерно восемь или девять worker-контекстов, используемых типичным проходом Full Mode, считаются по всему протоколу. Это **не** означает, что восемь или девять workers должны выполняться одновременно.

Расширяйте поисковую когорту до четырёх или пяти свежих worker-контекстов только после того, как шлюз покрытия выявит действительно отсутствующую причинную область.

## Правила свежего контекста

Не переиспользуйте worker для роли, ценность которой зависит от слепоты к материалу, который этот worker уже видел.

В частности:

- поисковые workers не должны видеть результаты других поисковых workers;
- screener не должен видеть результат mapper;
- mapper не должен видеть результаты screening;
- dossier workers должны видеть только одного финалиста каждый;
- adjudicator по slate должен быть свежим относительно поиска, screening, mapping и авторства dossier;
- reviewer для second opinion не должен видеть победителя adjudicator или предпочтение координатора.

Worker может получать все релевантные свидетельства о реальном мире. Независимость означает удаление прежних выводов и сигналов предпочтения, а не сокрытие фактов, необходимых для суждения.

## Целостность границ контекста

Штатный разговор worker через `agents` необходим для Full Mode в этой среде выполнения, но сам по себе он не является достаточным доказательством изоляции контекста.

Свежий worker может получить фоновый контекст, который не был явно включён в его `context` или `task`, включая контекст родительского разговора, пользовательский контекст, memory, history или контекст уровня проекта, переданный host-средой.

Поэтому различайте:

**Worker separation** — sibling workers напрямую не получают задания или результаты друг друга.

**Context isolation** — worker также не получает значимые для решения прежние выводы, framing, preferences или сведения о кандидатах через какой-либо другой канал контекста.

Full Mode требует второго свойства везде, где протокол зависит от изоляции или слепоты.

Для ролей, зависящих от изоляции, явная payload стадии является allowlist. Значимая для решения информация, унаследованная через parent history, memory, project context, shared summaries, retrieval или сохранённую worker history, считается contamination, если эта информация явно не разрешена для данной стадии.

Если требуется ранее известный факт реального мира, повторно внесите его в фактическую сводку с указанием происхождения. Не полагайтесь на фоновую память проекта или разговора для его передачи.

Спящий worker, возобновлённый через `agents message`, сохраняет существующую worker history и поэтому не является свежим для любой последующей роли, требующей слепоты к материалу, уже присутствующему в этой истории.

### Isolation preflight

Перед тем как полагаться на Full Mode после обновления Chat On Steroids/среды выполнения, а также перед публикацией benchmark-результатов, зависящих от изоляции workers, выполняйте небольшой smoke test границ контекста без чувствительных данных.

Используйте только синтетические sentinel labels; никогда не используйте приватные данные пользователя.

Проверьте три границы:

1. **Parent boundary**  
   Поместите безвредную sentinel declaration только в разговор prime. Запустите свежего worker, не включая эту declaration в его явные `task`/`context`. Спросите только, присутствует ли sentinel с таким label в его исходном контексте; не просите раскрывать скрытое содержимое.

2. **Sibling boundary**  
   Передайте безвредную sentinel declaration только worker A. Независимо запустите worker B. Спросите B только, присутствует ли материал sibling task с таким sentinel label; не просите его значение или содержимое.

3. **Persistence boundary**  
   Проверьте, что возобновление спящего worker сохраняет его собственную предыдущую историю. Считайте это positive control и никогда не переиспользуйте такого worker для роли, требующей слепоты к этой истории.

Записывайте каждую границу как:

- `PASS` — запрещённый фоновый контекст не был виден;
- `FAIL` — запрещённый фоновый контекст был виден;
- `INCONCLUSIVE` — среда выполнения не позволяет надёжно проверить эту границу.

`FAIL` или существенный `INCONCLUSIVE` на границе, необходимой для планируемой операции, означает, что эту операцию нельзя обозначать как Full Mode.

Успешный isolation preflight **не** является Phase B и сам по себе не удовлетворяет требованиям Full Mode. После preflight продолжайте с требуемой свежей поисковой когортой, если только шлюз активации не определит, что Full Mode для данного случая не нужен.

## Не обходите штатную привязку agents

Не запускайте Codex CLI, Claude Code, OpenCode, DevSpace или другой отдельный AI-процесс исключительно для имитации workers Convergence Guard, если пользователь явно не разрешил такую среду выполнения.

Не вызывайте workers через `curl`, скрытый локальный HTTP, прямой IPC, терминальные обходы или другой транспорт, обходящий привязку parent/worker в Chat On Steroids.

Перед длинным проходом Full Mode один раз проверьте фактическую доступность `agents` через штатный status-механизм. Наличие `agents` в опубликованной схеме инструментов необходимо, но недостаточно.

Если multi-agent support включена, но `agents` не виден в текущем разговоре, считайте это проблемой публикации инструмента или привязки сессии, а не доказательством отсутствия поддержки workers в Chat On Steroids.

Если реальный вызов завершается ошибкой до достижения локального Core с ошибкой connector/session, например `tool has been disabled` или `FORBIDDEN`, не повторяйте его вслепую в той же сломанной привязке. Сначала исправьте или пересоздайте соответствующее подключение/сессию.

Пока изолированные workers одновременно не видимы и не вызываются, не представляйте последовательное рассуждение в родительском контексте как Full Mode. Используйте [Reduced Mode](reduced-mode.ru.md) только с явного согласия пользователя.

## Дисциплина пользовательского интерфейса

Не перехватывайте экран пользователя, активное окно, мышь или фокус для фоновой аналитической работы.

Если задача действительно требует взаимодействия с GUI, следуйте активным правилам проекта и получите требуемое разрешение до перехвата фокуса.

## Восстановление после длинного прохода

Не перезапускайте весь протокол автоматически после задержки, перезагрузки или потери привязки worker.

Восстанавливайтесь в следующем порядке:

1. соберите результаты workers, которые уже завершились;
2. точно определите, какие операции фаз отсутствуют;
3. повторно запустите только отсутствующие workers или проверки;
4. сохраняйте замороженные артефакты screening/mapping, если они по-прежнему валидны;
5. продолжайте с ближайшей незавершённой операции;
6. никогда не заменяйте потерянный изолированный результат непомеченной последовательной реконструкцией в родительском контексте.

Не переключайтесь на другую внешнюю agent-среду для восстановления без явного разрешения пользователя.

## Сводка локального выполнения

```text
Chat On Steroids Core
→ evidence и состояние проекта
→ agents: изолированные worker-разговоры
→ замороженные артефакты слепых стадий
→ fresh adjudication по slate
→ convergence в родительском разговоре
```
